# 真正阻碍 AI Agent 普及的，可能不是模型能力，而是用户的表达成本

过去几年，AI Agent 的技术能力迅速提升。它们开始具备规划任务、调用工具、读取文件、操作外部系统、执行多步骤流程并在高风险动作前请求人工确认的能力。OpenAI 对 Agent 的定义也强调：Agent 不只是回答问题，而是能够代表用户管理工作流、选择工具并完成任务。[OpenAI：A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)

但在大量 Agent 产品中，用户与系统交互的主要入口仍然只是一个空白对话框。

这形成了一个值得重视的反差：Agent 的执行能力已经逐渐复杂，用户表达任务的方式却几乎没有变化。

## 被忽视的“意图表达成本”

一个空白对话框看起来简单、自由，似乎没有学习门槛。但这种简单往往只是界面层面的简单，它把大量工作转移给了用户。

例如，用户希望 Agent 帮忙起草一份公司通知。为了获得理想结果，他可能需要说明：

- 通知面向哪些人；
- 需要通知什么事项；
- 时间范围和截止时间；
- 语气应该正式还是亲切；
- 是否需要落款；
- 最终结果保存在哪里；
- 是否需要发送到飞书、邮件或其他系统。

熟悉 AI 的用户可能会主动组织这些信息，写出一个结构清晰的 Prompt。但对于大量普通用户而言，这并不是自然能力。

他们可能只会输入：

> 帮我写一份通知。

接下来，Agent 会不断追问；用户需要逐条阅读、记住问题、组织语言，再用自然语言回答。任务越复杂，用户越需要承担一种隐性的“需求分析”工作。

这可以称为 **意图表达成本**：用户为了让 Agent 正确理解目标，需要自行完成信息整理、任务拆解、参数补充和结果约束。

很多 Agent 产品关注模型是否足够聪明，却没有充分考虑用户是否有能力把需求表达得足够清楚。

## 空白对话框并不等于低门槛

自然语言交互的重要价值，是允许用户用不完整、不规范的方式发起任务。但自然语言不应该成为整个任务过程中唯一的交互形式。

当 Agent 已经知道下一步需要哪些确定信息时，继续要求用户自由打字，实际上是在浪费双方能力。

例如，Agent 已经判断起草通知需要：

1. 通知对象；
2. 具体事项；
3. 时间要求；
4. 落款信息。

这时最有效的交互不应该是：

> 请依次告诉我通知对象、具体事项、时间要求和落款信息。

而应该直接生成一个结构化界面：

- 通知对象使用选项按钮；
- 时间使用日期输入框；
- 语气使用单选项；
- 事项说明使用多行文本框；
- 必填信息明确标注；
- 常见答案直接提供候选项。

用户不再需要理解如何组织 Prompt，只需要识别选项并填写内容。

这不是削弱自然语言能力，而是在 Agent 已经理解任务结构之后，主动承担信息组织责任。

## 语音也不能完全解决问题

语音输入能够降低打字成本，但它不是通用答案。

用户可能处于办公室、会议室、公共场所或安静环境中，不方便持续说话。很多任务本身也包含日期、文件名、部门名称、金额和选项组合，这些信息通过语音表达容易产生识别错误，也不利于用户检查。

更重要的是，语音仍然要求用户在脑中组织完整表达。

一个用户可能不想说：

> 通知对象是上海分公司全体员工，放假时间是一月一日至一月七日，语气需要正式但亲切，落款使用行政部。

但他可以非常轻松地完成：

```text
通知对象：[全体员工]
放假时间：[1 月 1 日] 至 [1 月 7 日]
语气风格：[正式亲切]
落款部门：[行政部]
```

语音降低的是输入动作成本；结构化 UI 降低的是思考、组织和检查成本。两者解决的不是同一个问题。

## 从“对话优先”走向“自适应交互”

更成熟的 Agent 界面不应该在对话和传统表单之间二选一，而应该根据任务状态动态选择交互方式。

可以将它概括为：

> 自然语言负责表达开放意图，结构化 UI 负责收集确定信息。

用户首先可以模糊地说：

> 帮我起草一份通知。

Agent 理解目标后，不需要立即执行，也不需要继续抛出一长串文字问题，而是生成当前任务所需的交互组件。

这些组件并不是产品开发者提前为每一种场景手工编写的固定页面，而是 Agent 根据任务动态生成的临时界面。

```json
{
  "type": "form",
  "title": "补充通知信息",
  "fields": [
    {
      "key": "audience",
      "label": "通知对象",
      "kind": "select",
      "options": ["全体员工", "部门负责人", "指定项目组"]
    },
    {
      "key": "content",
      "label": "具体事项",
      "kind": "textarea",
      "required": true
    },
    {
      "key": "deadline",
      "label": "时间要求",
      "kind": "text"
    }
  ]
}
```

前端只负责安全地渲染受支持的组件，Agent 负责判断何时需要信息、需要什么信息，以及怎样组织这些信息。

这可以称为 **生成式交互界面**，或者 **Agent 驱动的自适应 UI**。

## 表单不是传统软件的倒退

有人可能认为，既然已经进入自然语言时代，再使用表单是一种倒退。

这种判断混淆了固定流程与动态结构。

传统软件的问题不是表单本身，而是所有用户都必须适应开发者预先规定的固定流程。用户需要寻找正确页面、理解字段含义，并按照系统设计完成操作。

Agent 驱动的表单则不同：

- 它只在需要时出现；
- 字段由当前任务动态决定；
- 已知信息不重复询问；
- 用户可以随时改用自然语言；
- 表单提交后，Agent 自动继续任务；
- 下一次需要的信息可以生成完全不同的界面。

传统软件要求用户理解系统结构；自适应 UI 则要求系统理解用户目标。

因此，这不是回到旧软件，而是让结构化交互第一次具备上下文感知能力。

## Agent 不应只会执行，还应帮助用户定义任务

目前大量 Agent 架构把重点放在：

- Planner 如何规划；
- Tool 如何调用；
- Context 如何压缩；
- Evaluator 如何判断完成；
- 多 Agent 如何协作；
- MCP 如何连接外部能力。

这些问题当然重要。Anthropic 也建议 Agent 系统从简单、可组合的模式开始，并根据实际价值逐步增加复杂度，而不是一开始追求复杂编排。[Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

但在真正面向普通用户的产品中，还需要补上一层：

> Agent 如何帮助用户把一个模糊愿望逐渐定义成可执行任务？

这个过程不应该完全依赖用户掌握 Prompt 技巧。

Agent 应该能够：

1. 判断当前信息是否足够；
2. 识别缺失的关键字段；
3. 选择合适的输入组件；
4. 提供常见选项和示例；
5. 校验日期、范围和逻辑冲突；
6. 将结构化结果放回同一个 Task；
7. 在信息充分后自动恢复执行。

用户负责作出选择，Agent 负责组织问题。

## 一种更完整的人机协作循环

这种设计可以形成如下循环：

```text
用户表达模糊目标
        ↓
Agent 理解目标并判断信息缺口
        ↓
生成结构化交互界面
        ↓
用户选择、填写或修正
        ↓
Agent 获得结构化输入
        ↓
继续规划和执行
        ↓
高风险动作请求确认
        ↓
生成结果并保留执行记录
```

在这个循环中，对话框不再是唯一入口，而是一个容纳多种交互形式的工作空间。

其中可以出现：

- 自然语言消息；
- 单选和多选；
- 日期与时间输入；
- 文件选择；
- 表格字段；
- 审批确认；
- 结果预览；
- 错误修正；
- 执行步骤。

对话仍然存在，但它从纯文本聊天升级为动态任务界面。

## 设计这种系统需要注意什么

自适应表单并不是越多越好。

如果 Agent 对一句简单问题也生成复杂表单，系统会变得僵硬。因此，需要明确边界：

### 简单问题直接回答

例如：

> 今天星期几？

不需要表单。

### 信息缺口明确时生成表单

例如起草通知、整理会议纪要、创建定时任务、批量处理文件，都适合结构化收集参数。

### 保留自由文本入口

用户应始终能够输入“都不是”“情况比较特殊”或直接补充背景。

### 使用渐进式披露

只询问当前真正需要的信息，不一次展示十几个字段。

### 不伪造确定性

如果 Agent 不确定应该问什么，应先进行简短澄清，而不是生成看似专业但方向错误的表单。

### 高风险动作单独确认

发送消息、修改文件、执行命令和更新外部数据，不应该混在普通表单提交中。OpenAI 的 Agent 实践指南同样强调，高风险或不可逆动作应设置明确的人类介入机制。[OpenAI Agent 实践指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)

## 从“会使用 AI”到“AI 帮助人完成工作”

当前很多 AI 产品实际上仍然要求用户先成为一个优秀的 AI 使用者。

用户需要知道：

- AI 能做什么；
- 任务应该如何拆解；
- Prompt 应该怎样写；
- 文件路径是什么；
- 输出格式如何描述；
- 哪些信息需要提前提供。

这限制了 Agent 的真正普及。

更合理的方向不是培训所有人学习 Prompt Engineering，而是让 Agent 主动完成一部分需求分析和交互设计工作。

用户不需要想象完整工作流，只需要表达最初目标。Agent 根据目标逐步生成适合当前场景的界面，引导用户补充必要信息，并把这些信息转化为可以执行的任务。

这种设计哲学可以概括为：

> 不要求用户学习如何正确地向 AI 描述工作，而是让 AI 学会如何帮助用户把工作描述清楚。

未来真正面向大众的 Agent，竞争力可能不只来自更强的模型、更丰富的工具和更长的上下文，也来自一个更基础但经常被忽视的能力：

> 它是否能够降低普通人表达需求、理解流程和作出选择的认知成本。

当 Agent 不仅能执行任务，还能主动生成适合用户的交互界面时，它才有机会从“高级聊天工具”真正转变为普通人的数字助理。
